# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Vision

Tablas aims to become a JetBrains-style data-file editor for VS Code (think DataGrip's/IntelliJ's built-in table viewer): open a data file, see a real table, search it, edit a cell, done. See `README.md` for the user-facing pitch.

Current stage: local install only (`npm run install:local`, unpublished). Target: publish to the VS Code Marketplace under publisher `gerardovitale`. Keep marketplace-readiness in mind for anything packaging/metadata-related. The `package.json` metadata (`displayName`, `description`, `categories`, `keywords`, `icon`), `icon.png` and `CHANGELOG.md` (required by `vsce`; keep its `[Unreleased]` section current) exist. Still outstanding before a first `vsce publish`, in `BACKLOG.md`'s release order: a real-window smoke test (V-1), a stable DuckDB pin (V-2), bundling and trimming the `.vsix` (P-2) and per-platform `.vsix` builds (P-3). See `scripts/install-local.sh --publish-help` for the full publishing checklist.

Today: CSV, Parquet, SQLite (`.db`/`.sqlite`/`.sqlite3`), DuckDB (`.duckdb`/`.ddb`; with live refresh, a read-only SQL box and light dbt support), and Excel (`.xlsx`), read-only. Planned, roughly in order:
1. **Column sort** (`BACKLOG.md` T-1) — host-side over the whole table, like filters.
2. **In-table find** (T-2) — search within the rendered table (not VS Code's plain-text Ctrl+F). Per-column *filtering* has already shipped; see "Column filtering" below.
3. **Basic cell editing** — writes back to the source file; requires moving off `CustomReadonlyEditorProvider` to a real edit model (dirty state, undo/redo, save).

Open follow-ups (known gaps in shipped features, perf/cleanup, manual checks not yet done) live in `BACKLOG.md`; when one ships, delete it there and note it in `CHANGELOG.md`.

Keep this trajectory in mind when touching the architecture below:
- New single-table source formats should get their own parser module (parallel to `csvParser.ts`/`parquetParser.ts`) that produces the *same* `{headers, rows, rowCount, columnCount}` shape (`ParsedTable` in `src/tableData.ts`), so `src/webview/main.js` doesn't need to know or care what format it came from. New *multi-table* sources (parallel to `sqliteParser.ts`/`duckdbParser.ts`) instead produce `MultiTableParseOutcome`.
- The extension-host-parses / webview-only-renders split is the thing to preserve — don't add format-specific logic to the webview.
- Editing support will need a real `vscode.CustomDocument` implementation (currently `CsvDocument`/`ParquetDocument` are bare stubs) plus an edit/undo model — flag this explicitly if asked to implement editing rather than quietly bolting writes onto the read-only provider. `SqliteDocument`/`DuckdbDocument` are already a partial exception: each holds a live database handle (see below), but still only for read access.

## Architecture

Two independent esbuild bundles come out of `esbuild.js`, built together by `npm run compile`:

- `dist/extension.js` — CJS, Node platform, entry `src/extension.ts`. This is the extension host code (`main` in package.json). `papaparse`, `hyparquet`, and `exceljs` are fully bundled in here (all pure JS, no `.wasm`/native asset); `sql.js` and `@duckdb/node-api`/`@duckdb/node-bindings` are kept `external` instead (see below).
- `media/webview.js` — IIFE, browser platform, entry `src/webview/main.js`. This runs inside the VS Code webview sandbox.

**Parsing happens only in the extension host, never in the webview.** `src/csvParser.ts` wraps PapaParse and returns a `CsvParseOutcome` discriminated union (`{success: true, data, errors}` or `{success: false, errors}`). `src/csvEditorProvider.ts` reads the file, calls `parseCsv`, and posts the result to the webview as a `csv-data` message. `src/parquetParser.ts`/`src/parquetEditorProvider.ts` mirror this exactly for `.parquet`. The webview (`src/webview/main.js`) only renders pre-parsed data — it has no format-parsing logic and imports nothing from the parser modules at runtime (only referenced in JSDoc type imports).

`CsvEditorProvider` (registered as `tablas.csvViewer`, a `CustomReadonlyEditorProvider`) does a ready-handshake: it waits for a `{type: 'ready'}` message from the webview before it reads/parses the file and posts `{type: 'csv-data', payload: outcome}` back. Webview HTML is built per-request with a fresh CSP nonce (`crypto.randomBytes(16)`) and `script-src 'nonce-...'`; `default-src 'none'`.

All DOM writes in `src/webview/main.js` use `textContent`/`setAttribute` only — never `innerHTML` — this is a deliberate XSS-safety rule for any rendered cell/header content, since file content is untrusted. `eslint.config.js` has a `no-restricted-syntax` rule making this machine-checked (bans `innerHTML`/`outerHTML` assignment).

### SQLite (multi-table sources)

`.db`/`.sqlite`/`.sqlite3` files (registered as `tablas.sqliteViewer`) are the first *multi-table* source and deviate from the CSV/Parquet pattern in three ways:

- **Library**: `sql.js` (WASM SQLite), not a native binding — a single `.wasm` asset works on every platform VS Code runs on, avoiding a per-OS/arch `.vsix` matrix. It's `external` in `esbuild.js`'s extension bundle (can't be inlined — a `.wasm` binary isn't JS text) and `sqliteParser.ts` locates it via `require.resolve('sql.js/dist/sql-wasm.wasm')`.
- **Data shape**: `src/tableData.ts`'s `MultiTableParseOutcome`/`MultiTableData`/`TableRef` wrap a list of tables/views plus the currently-selected one's `ParsedTable`, additively alongside (not replacing) the single-table `TableParseOutcome` CSV/Parquet use.
- **Stateful document + bidirectional messaging**: unlike `CsvDocument`/`ParquetDocument`'s bare stubs, `SqliteDocument` (in `sqliteEditorProvider.ts`) holds the live `SqliteHandle` for the document's lifetime, so switching tables re-queries the already-open database instead of re-reading the file. `SqliteEditorProvider`'s `onDidReceiveMessage` listener stays registered after the ready-handshake (CSV/Parquet's disposes itself) to also handle `{type: 'select-table', table}` requests, responding with the same `sqlite-data` message type used for the initial load. The webview (`renderMultiTableOutcome`/`renderTableSelector` in `main.js`) renders a table picker above the table and posts `select-table` when a different table is chosen. The picker (`renderTableSelector`, shared by SQLite/XLSX/DuckDB) is a trigger button plus a searchable ARIA combobox/listbox popup, not a native `<select>` (which painted white on dark themes and has no search): the search input keeps focus and `aria-activedescendant` names the active option; Tables/Views group headers show only when a source has both kinds; match highlighting uses text nodes + `<mark>` only. After a pick the new render re-focuses the new trigger if the old one had focus. Styling lives in the "Table picker" section of `media/styles.css`; `color-scheme` is set from VS Code's `body.vscode-*` theme classes.

### XLSX (multi-table sources)

`.xlsx` files (registered as `tablas.xlsxViewer`) are the second multi-table source, reusing the exact same `MultiTableParseOutcome`/`select-table` protocol SQLite established (a workbook's sheets fill the role SQLite's tables/views do) — no webview changes were needed beyond routing a new `xlsx-data` message type to the already-generic `renderMultiTableOutcome`.

- **Library**: `exceljs`, not SheetJS's `xlsx` package — deliberately. npm's published `xlsx` is stuck at `0.18.5` with two unfixed high-severity CVEs (ReDoS + prototype pollution) triggerable by opening a crafted file; SheetJS only ships the fix via their own CDN, not npm. Since this extension's whole job is parsing untrusted file bytes, that's a direct hit on the threat model — `exceljs` has no comparable CVE in its own runtime parse path. It's pure JS (no `.wasm`), so — like `hyparquet`/`papaparse` and unlike `sql.js` — it needs no `external`/`.vscodeignore` treatment; see `xlsxParser.ts`'s `openXlsxWorkbook` for the `Buffer` typing workaround its `.d.ts` needs (an ambient `Buffer` interface it declares conflicts with `@types/node`'s generic one).
- **Cell stringification**: `stringifyXlsxCell` (in `xlsxParser.ts`) sends **Date values** (plain cells, formula results, merged cells — found via `unwrapCellValue`) through `formatXlsxDate`, and delegates everything else to exceljs's own `cell.text` getter, which resolves formulas to their cached result — unlike `parquetParser.ts`'s `stringifyCell`, no further type-switching is needed. `formatXlsxDate` writes ISO text from the Date's **UTC** fields (exceljs's `excelToDate` stores Excel's wall-clock there, so the text is timezone-independent), and the cell's number format picks date (`2024-01-01`), time (`10:30:00`) or both (`2024-01-01 10:30:00`); with no usable format a midnight value is a date. Elapsed-time sections (`[h]`, `[mm]`, `[s]`) count as time tokens, but durations of 24 h or more wrap. `cell.text` alone would give `Date.toString()`. The statistics card's date min/max use the same text. The fallback reads `cell.master.text`, not `cell.text`, because exceljs's `MergeValue.toString()` prints `[object Object]` for the other cells of a range whose master is a formula; formula **error** results are read from the unwrapped value for the same reason. Note `cell.text` does **not** apply the cell's number format to numbers (a `0%` cell shows `0.5`), and renders a formula result of `0`/`false` as `''`.
- **Stateful document + bidirectional messaging**: same shape as SQLite — `XlsxDocument` (in `xlsxEditorProvider.ts`) holds the parsed `Workbook` for the document's lifetime (nothing to `.close()`, unlike `SqliteHandle`), and `XlsxEditorProvider`'s message listener stays registered post-handshake to handle `{type: 'select-table', table}` (the field is still named `table`, reused as-is from the SQLite protocol) by re-reading the already-parsed workbook for a different sheet.

### DuckDB (multi-table sources)

`.duckdb`/`.ddb` files (registered as `tablas.duckdbViewer`) are the third multi-table source, reusing the same `MultiTableParseOutcome`/`select-table` protocol via a new `duckdb-data` message type routed to the already-generic `renderMultiTableOutcome` — no webview changes beyond that one dispatch line.

- **Library**: `@duckdb/node-api` (the official Node "Neo" client), a **native** N-API binding — a deliberate departure from `sql.js`'s WASM-for-portability precedent (see the SQLite section above), chosen for full DuckDB SQL support and native speed. Its per-platform binary (`@duckdb/node-bindings-<platform-arch>`, ~100+ MB uncompressed, resolved transitively via `@duckdb/node-bindings`) means a single `.vsix` is no longer portable across platforms the way `sql.js`'s one `.wasm` file was — see the Packaging note below. Both `@duckdb/node-api` and `@duckdb/node-bindings` are `external` in `esbuild.js` (a native `.node` binary can't be bundled by esbuild), and both need narrow `.vscodeignore` allowlist entries (see the flat-negate gotcha below).
- **Bytes vs. path**: unlike `sql.js`/`exceljs`, `@duckdb/node-api` opens a database from a file *path*, not an in-memory byte buffer. To keep `parseDuckdb(bytes, ...)` symmetric with `parseSqlite`/`parseXlsx` (same signature, same fixture-bytes unit-test style, and correctness over non-local `vscode.FileSystemProvider` filesystems), `duckdbParser.ts`'s `openDuckdbDatabase` writes `bytes` to a temp copy and opens DuckDB against that; `DuckdbHandle.close()` deletes it alongside closing the connection/instance. **The copy keeps the source file's name**, in a private `tablas-db-*` folder under `os.tmpdir()` (`options.fileName`, passed by the provider from the URI; `tempCopyName` sanitizes it): DuckDB derives a database's *catalog name* from its file name, and a view written by DuckDB 1.x (every dbt-duckdb project) stores references to its own catalog verbatim (`FROM warehouse.main.stg_orders` in `warehouse.duckdb`), so a copy called `tablas-1a2b.duckdb` fails reading such a view with `Table with name "warehouse.main.stg_orders" does not exist because schema "warehouse.main" does not exist`. DuckDB 2.x strips the own-catalog reference when it *creates* a view, so fixtures written by the bundled engine cannot show this: `test/fixtures/qualified-views.duckdb` is written by `scripts/generate-duckdb-legacy-fixtures.py` (needs `pip install "duckdb<2"`) and the regression test asserts the exact error for an unnamed copy.
- **Read-only opens**: `openDuckdbDatabase` always opens with `{ access_mode: 'READ_ONLY' }` so the viewer never mutates the source file. This means any test that needs to *write* to a DuckDB file (e.g. building an ad-hoc fixture inline) has to go around `openDuckdbDatabase` and use `DuckDBInstance.create` directly, the same way `scripts/generate-duckdb-fixtures.js` does.
- **Cell stringification**: `stringifyDuckdbCell` (in `duckdbParser.ts`) consumes `DuckDBResultReader.getRowsJson()`, which already reduces DuckDB's richer type system (BIGINT/HUGEINT/DECIMAL/DATE/TIMESTAMP/UUID/BLOB, etc.) to JSON-safe strings/numbers/booleans — notably, BIGINT comes through as an exact string, avoiding the precision loss `stringifySqliteCell` accepts as a known limitation for sql.js's plain-`number` BIGINTs. Only nested LIST/STRUCT/MAP/ARRAY/UNION values need any handling here (via `JSON.stringify`), similar in spirit to `parquetParser.ts`'s `stringifyCell`.
- **Engine version caps readable files**: DuckDB storage is backward- but not forward-compatible, so the bundled `@duckdb/node-api` version is the newest file it can open (1.5 reads storage 64-68 and rejects what 2.x writes as "version number 999"). Keep it current with DuckDB releases. `openDuckdbDatabase` rewords that failure via `describeDuckdbOpenError`. `test/fixtures/storage-v2.duckdb` (regenerate alone with `node scripts/generate-duckdb-fixtures.js storage-v2`) covers 2.x files; the older fixtures are storage v64 and cover backward compat, so don't regenerate them without need.
- **Relative paths in views**: the database is opened from a temp copy, so a view such as `read_parquet('../data/*.parquet')` would resolve against the extension host's cwd. `openDuckdbDatabase(bytes, { searchDir })` runs `SET file_search_path` with the source file's folder (the provider passes it for `file:` URIs only; a folder containing a comma is skipped because the setting is comma-separated). If reading the selected table still fails, `readSelectedTable` returns `tableError` (with empty `data`) instead of throwing, and the webview shows it under the selector, so one bad view does not hide the other tables.
- **Table/view listing and schemas**: `listDuckdbTables` (memoized per handle in `tableLists`, but still routed through `runExclusive` so callers that list first and then check whether a newer request overtook them keep that wait) joins `information_schema.tables` (`table_type = 'VIEW'` vs. everything else) with `duckdb_tables()` and lists **every schema** of the file's own catalog except `information_schema`/`pg_catalog`, ordered `main` first, then schema, then name. `TableRef.name` is the unique id used by `select-table`, stats, filters and `workspaceState`: bare for `main` (so a name stays valid however many schemas the file gains, which matters for reload), `schema.table` otherwise, with `schema`/`table` set only then. (A `main` table literally named `a.b` would collide with schema `a` table `b`; not handled.) The refs are cached per handle in `tableRefs` and `quotedTableName(handle, name)` turns a name into `"schema"."table"` for the reads, stats and filter SQL; a name that was never listed is a bare `main` table, so tests that skip `listDuckdbTables` still work, but every provider path lists first. `TableRef.approxRows` is `duckdb_tables().estimated_size` (no scan; views have none). The webview groups the picker by schema only when the refs span more than one (a ref without `schema` counts as `main`), showing `ref.table` under the header and `ref.name` as the tooltip/trigger text; a single non-main schema is listed flat with qualified names. Fixture `schemas.duckdb` (`node scripts/generate-duckdb-fixtures.js schemas` writes only it; a bare run rewrites every fixture, including the storage-v64 ones, so `git checkout` the rest).
- **SQL box** (`capabilities.query`): protocol in the vscode-free `src/queryMessage.ts` (`{type:'run-query', seq, sql}` -> `{type:'query-data', payload:{seq, data?, truncated?, elapsedMs?, error?}}`; `QueryOutcome` lives there too). `duckdbRunQuery(handle, sql, maxRows, {shouldRun})` in `duckdbParser.ts` is the engine; the provider's public `handleRunQuery` adds the `querySeq` drop (an older request still queued never runs, `shouldRun` is asked at the front of the `runExclusive` queue) and keeps the text in `workspaceState` (`tablas.lastQuery:<uri>`, sent back as `MultiTableData.lastQuery`; `querySuggestion` is `suggestQuery(handle, selectedTable)`). **Read statements only**: every statement is `prepare`d first (binds, does not execute; an `EXPORT` still creates its empty folder while binding) and its `statementType` must be SELECT (covers WITH/FROM-first/SHOW/DESCRIBE/SUMMARIZE and the read-style pragmas such as `PRAGMA table_info(..)`), EXPLAIN or MULTI (what PIVOT expands to), else the whole text is refused with an error before anything runs. PRAGMA and CALL are **not** allowed types: assigning pragmas come typed SET (`PRAGMA profiling_output = 'f'` would redirect a file every later query writes), and CALL runs functions with side effects (`SELECT * FROM fn()` covers the read-only ones). **`EXPLAIN ANALYZE` is refused** by a text match for the word `analyze`/`analyse` on any EXPLAIN statement: it is typed EXPLAIN but *executes* what it explains (`EXPLAIN ANALYZE COPY .. TO 'f'` writes the file; reproduced). This is a guard against slips on the user's own machine, not a sandbox. Not left to the read-only open: `COPY .. TO` writes files and `INSTALL`/`LOAD`/`ATTACH` reach outside the file even on a READ_ONLY database, and the webview re-runs its last query after every refresh, so a side effect would repeat on each `dbt build`. The result is **streamed** (`streamAndReadUntil(sql, maxRows + 1)`) so `SELECT *` on a huge table never materializes, and the reader **must be `closeSync()`ed in `finally`**: a result left open makes every later request on the connection fail with "connection has an open result" (a unit test fails without it). Time budget `queryLimits.duckdbTimeoutMs` (30 s) via `interrupt()`, text limit `queryLimits.maxSqlLength` (100k; the textarea's `MAX_QUERY_LENGTH` mirrors it). **Webview**: Table/SQL mode, text, last result and the run counter are module state (they must survive the re-render every payload causes); `renderTable(data, undefined, undefined, {host, result})` draws a result without the filter row and without `get-stats` (both are keyed by a table the host knows). The picker is hidden in SQL mode. A reload payload re-runs `queryRunSql` (the SQL behind the result on screen, not unsent edits) and keeps the old result until the answer lands; if a run is still in flight the refresh only sets `queryRerun`, which re-runs once after that answer (the host already drops queued older requests by `seq`, but never cancels a running one); focus, caret and scroll of the box and the result's scroll survive the rebuild (`captureQueryUiState`/`restoreQueryUiState`, `queryScrollToRestore` for the re-run's answer); entering SQL stashes the table's filters/scroll in `savedTableState` and Table restores them. `renderMultiTableOutcome(outcome, {rerender: true})` redraws the last payload for the toggle without the stale-reply check or reload handling.
- **SQL highlighting and theme colours**: the query box is the same `<textarea class="query-input">` (so selection/undo/IME/a11y stay the browser's) with `color`/`-webkit-text-fill-color: transparent`, inside `.query-editor` over an `aria-hidden` `<pre class="query-highlight">` that `paintSqlHighlight` redraws from `tokenizeSql(text)` on every `input` (a frame later above `SQL_SYNC_HIGHLIGHT_LIMIT`, 20k characters) and whose `scrollTop/Left` follow the textarea's. **The two must lay out the text identically**: they share every font/box property in one CSS rule, neither wraps (`wrap="off"`, `white-space: pre`), both `overflow: auto` (the layer's scrollbar is transparent but takes the same room, so the visible areas match), and a text ending in `\n` gets one extra character in the layer. If you change padding, font or line height, change it in that shared rule only; verify alignment in a real browser (jsdom has no layout) by comparing `clientWidth/clientHeight/scrollWidth/scrollHeight` of the two. The tokenizer is a single forward pass (strings with doubled-quote escapes, `--`/`/* */`/`$$ $$`, numbers, `ident(` = function, keyword/type/constant sets, operators; never throws, always reproduces the text exactly: a test fuzzes that). The keyword/type sets are static lists in `main.js`. **Colours**: the host sends `{type:'sql-theme', colors}` (`src/sqlTheme.ts`, vscode-free: `SqlThemeMessage`, `resolveSqlColors`, `customizationRules`, `parseJsonc`; `src/sqlThemeHost.ts`, the vscode part, excluded from c8: finds the active theme among `vscode.extensions.all` by label/id: VS Code gives an extension no theme *name*, and `workbench.colorTheme` is the wrong one when `window.autoDetectColorScheme` is on (it keeps the other scheme's theme), so `candidateThemeNames` (in `sqlTheme.ts`) lists `workbench.preferred<Dark|Light|HighContrast...>ColorTheme` first when auto-detecting and the host takes the first whose contributed `uiTheme` equals `vscode.window.activeColorTheme.kind`; reads its `tokenColors` following `include`s, adds `editor.tokenColorCustomizations` incl. the `[Theme]` block, caches by theme+customizations) after the ready handshake and again on `onDidChangeActiveColorTheme`/`onDidChangeConfiguration` (for any of `SQL_THEME_SETTINGS`). Scope matching is a **simplification of TextMate's** (dotted-prefix selectors, longest wins, later wins ties, parent parts must be `source.sql`, `-`/`|`/groups ignored); each token class lists the scopes VS Code's SQL grammar gives it in `SQL_TOKEN_SCOPES`. The webview sets `--sql-<class>` on `documentElement` through CSSOM **only for `#rgb[a]`/`#rrggbb[aa]`** values (a message must never inject CSS) and `removeProperty`s the rest; `.sql-<class>` reads `var(--sql-<class>, var(--sql-default-<class>))`, and the defaults live on `body` (dark) / `body.vscode-light, body.vscode-high-contrast-light` (never on `.query-editor`, or they would shadow the light ones).
- **dbt support (light, optional)**: `src/dbt.ts` is the vscode-free core (project root via walking up to `dbt_project.yml`, `name:`/`target-path:` read with two line patterns rather than a YAML parser, `indexManifest`/`loadDbtManifest` with an mtime+size cache and a 300 MB cap, `findNodeForFile`, `findTableRef`, `columnDescriptionsFor`); `src/dbtCommands.ts` is the vscode layer (excluded from c8 like the providers): the `tablas.dbtProject` context key (set by scanning `**/dbt_project.yml`, rescanned by a watcher), `getDbtProjectRoots()` (the provider's fallback when the DuckDB file is not under a project and the workspace has exactly one), and `tablas.previewDbtModel`, which returns a `PreviewResult` string (tests read it). The extension activates on `workspaceContains:**/dbt_project.yml` so the menu items can appear. `columnDescriptionsFor` goes through `findProjectRootCached` (per folder, 30 s TTL) and `readProjectCached` (until the file's mtime/size changes); `clearDbtProjectCache()` is called by the `dbt_project.yml` scan in `dbtCommands.ts`, and tests that create/delete a project in a reused folder must call it. **Manifest facts relied on**: `nodes`/`sources` entries with `resource_type`, `name`, `alias`, `identifier` (sources), `schema`, `database`, `package_name`, `original_file_path` (relative to the *package* root, forward slashes; two packages can share `models/foo.sql`, so `findNodeForFile` with a known project name returns only the project's own node, and a not-yet-built file never resolves to an installed package's), `config.materialized`, `columns.<name>.description`. For dbt-duckdb `database` is the DuckDB file's name without extension, which is how the file is found (`**/<database>.{duckdb,ddb}`, else any DuckDB file, one match used as is, several offered in a quick pick). Names match case-insensitively (`relationKey`, `findTableRef`) because dbt keeps the author's case and DuckDB does not care; `TableRef`s of `main` match on `schema ?? MAIN_SCHEMA`. **Descriptions only attach to the database dbt built them in**: `relationForFile` keeps nodes whose `database` equals the DuckDB file's name without extension (case-insensitive; a node without `database` matches any file) and prefers the project's own package, so a `scratch.duckdb` with a `main.orders` of its own never shows the model's docs. The manifest path is `path.resolve(root, target-path, 'manifest.json')` (`manifestPath`), so an absolute `target-path:` works. **Reveal flow**: `DuckdbEditorProvider.revealTable(uri, {schema, table})` -> if the panel is open, `selectors` has its `select` (which posts `duckdb-data` with `MultiTableData.hostSelected`, so the webview adopts the table even over a pick still in flight and leaves the SQL box; if that table is already the one shown it only brings the panel forward, so filters, scroll and the query result survive; a failed select is not pushed, while a fallback table is, so the host and the webview agree). **Ordering**: `handleSelectTable` bumps `document.selectSeq` and publishes nothing if a newer switch started while it awaited (the descriptions await takes real time), `handleReload` attaches descriptions *inside* its `wanted()` retry loop so a pick during that await re-reads instead of being overwritten by `publish`, and a panel's dispose only removes its own `selectors` entry; if not, `pendingReveals` + `awaitFirstLoad` + `vscode.openWith`, and `loadInitial` opens on it (beating the remembered table, and remembering it like a pick) and settles the promise (`'shown'`/`'missing'`, `'unavailable'` from the `finally` or after 15 s). **Descriptions**: `withColumnDescriptions` adds `MultiTableData.columnDescriptions` on first load, table switch and reload (a manifest changed by `dbt parse` alone does not trigger a refresh by itself; the next reload or switch picks it up); the webview matches column names ignoring case (`view.descriptions`, header `title` + `has-description` mark, `card-description` paragraph), as text only. Fixture project: `test/fixtures/dbt/` (its `database` is `schemas`, so the command finds `test/fixtures/schemas.duckdb`).
- **Last table per file**: `handleSelectTable` stores the shown table under `workspaceState` key `tablas.lastTable:<uri>` (only when it read without `tableError`); `loadInitial` (public for tests) passes it as the desired table, and `readSelectedTable` falls back to the first one if it no longer exists. `context.workspaceState` is optional in code because tests build the provider with a bare context.
- **Stateful document + bidirectional messaging**: same shape as SQLite/XLSX — `DuckdbDocument` (in `duckdbEditorProvider.ts`) holds the live `DuckdbHandle` (and its temp file) for the document's lifetime, and `DuckdbEditorProvider`'s message listener stays registered post-handshake to handle `{type: 'select-table', table}`. One difference: `handleSelectTable` is `async` here (DuckDB reads are all promise-based), unlike `SqliteEditorProvider`'s synchronous version.
- **Live refresh** (dbt loop): `DuckdbEditorProvider.resolveCustomEditor` watches the file and its `.wal` (non-recursive `createFileSystemWatcher` over the whole folder with `*`, filtered by exact path in the handler because a pattern built from the file name misfires for names with glob characters; `file:` URIs only) and feeds events to `ReloadScheduler` (`src/reloadScheduler.ts`, vscode-free so it is unit tested with fake timers): 750 ms debounce, then keep waiting while `<file>.wal` exists (the writer has not checkpointed; copying now would show a half-applied state), but never longer than 30 s after the first event of a burst (a crashed writer leaves its `.wal`). `handleReload(document)` (public; integration tests call it) re-reads the bytes into a **new** handle first and only then swaps `document.handle`; on any failure (unreadable, empty, corrupt, or the shown table cannot be read: `tableError` counts as a failed reload, so a view whose source files vanish mid-build never replaces a good view) the old handle and view stay and `{type:'reload-status', state:'failed', message}` is posted instead of `duckdb-data`. The old handle closes via `runExclusive(old, noop).then(close)` so queued queries finish, and a document disposed mid-reload closes the handle it just opened. A successful reload posts a normal `duckdb-data` with `MultiTableData.reload` (`at`, `previousRowCount` only when the same table is shown) and `capabilities.refresh`; `publish()` stamps both and remembers `document.selectedTable`/`shownRowCount`. The table is read from `document.selectedTable` and re-read (up to 3 times) if a pick changed it meanwhile, so a reload never records a table the user left. If the first load failed or found an empty file (`document.initialLoadDone` true, no handle), a successful reload *is* the first load; `loadInitial` assigns `document.handle` only after its first read, and `runReload` waits for it. Only one reload runs at a time (`reloadQueued` re-runs once). Triggers: watcher, webview `{type:'refresh'}` (toolbar `↻`), command `tablas.refresh` (`refreshActive` finds the active custom-editor tab). Setting `tablas.autoRefresh` gates only the watcher. Known gap: the `.wal` is **not** copied, so while a long-lived writer holds uncheckpointed data, the 30 s cap reloads without it. **Webview**: the toolbar (`.table-toolbar`: picker + button + `.reload-status`) gates on `capabilities.refresh`, never on format. On a reload payload `captureReloadState`/`restoreReloadState` re-apply filter text (only if table name and headers are unchanged; scroll is restored after the filter reply via `view.pendingScroll`), scroll and the focused filter box. `renderMultiTableOutcome` drops any payload whose table differs from the user's last pick *while that pick still exists in the payload's table list* (stale select replies and slow reloads alike); if the picked table is gone from the file, the host's fallback table wins. On a reload `renderTable` is called with `deferStats` and `requestStats()` runs *after* `restoreReloadState`, so the filter request is queued before the whole-table stats scan (a new handle has an empty `StatsCache`); with a filter to re-apply the tbody is emptied (`view.rowsHidden`) until its reply lands, and `restoreOriginalRows` brings the table back if the reply is `invalid`/`failed`. A SQL result made old by a reload while Table mode shows is not re-run in the background: `queryStale` re-runs it when the box opens again. Identical `reload-status` text is not rewritten (live region), and `view.pendingScroll` is consumed once by whichever way the reload's own filter request ends (applied/invalid/failed) and cleared by any filter the user sends.

**Packaging note**: `scripts/install-local.sh` runs a plain `vsce package` (no `--target`), which is fine for local single-machine install since npm only installs the dev machine's matching `@duckdb/node-bindings-<platform-arch>` package. A future Marketplace publish will need **per-platform `.vsix` builds** (`vsce package --target darwin-arm64`, etc.) — add this to the "outstanding before `vsce publish`" list above when that work starts; it hasn't been built yet.

### Column statistics

Column statistics (`TableStats`/`ColumnStats` in `src/tableData.ts`; `columns[i]` parallels the table's headers) are **requested separately from rows, but always**: rows are posted first and never carry stats. Right after the webview renders a table (first load and every table switch) it posts `{type:'get-stats', table?}` and the provider answers `{type:'stats-data', payload:{table?, stats?}}` (types + guards in the vscode-free `src/statsMessage.ts`). `stats` undefined = failed; `skippedReason` inside it = deliberately skipped. The echoed `table` lets the webview drop a stale reply. Stats cover the **whole table** (never limited by `tablas.maxRows`). There is deliberately no way to turn them off, so every open pays for one stats pass (after the rows are already on screen); the per-parser caps/timeouts below are what bound that cost.

`get-stats` carries a webview-wide `seq` (never reset, like `filter`'s) that `statsDataMessage(payload, seq)` echoes; `handleStatsData` applies a reply only when `table` **and** `seq` match the view's own request, because after a reload the same table is drawn again while the old handle's scan may still be running. Each provider exposes a public `handleGetStats(document, table?)` next to `handleSelectTable` (integration tests call it directly — a webview→host message can't be simulated) and answers it from the same persistent message listener. **CSV and Parquet keep no parsed state for stats, so they re-read (and re-parse) the file on demand** rather than hold rows/bytes for the editor's lifetime (filtering is the one exception: see "Column filtering"); a file edited on disk in between yields stats for its newer content. XLSX/SQLite/DuckDB use the workbook/handle the document already retains.

Why stats live in the parsers: every parser stringifies cells and maps NULL to `''`, so types and nulls are gone once `rows` exists. Each parser exports a standalone entry point that computes from native values (CSV/XLSX/Parquet) or SQL push-down (SQLite/DuckDB): `csvStats(raw)`, `xlsxSheetStats(ws)`, `parquetStats(bytes)`, `sqliteTableStats(handle, table)`, `duckdbTableStats(handle, table)`. All return `TableStats | undefined`, never throw, and report unexpected errors through `statsHooks` (`console.warn` by default).

- `src/columnStats.ts` (no `vscode` import) holds the shared pieces: `ColumnStatsAccumulator` (CSV/XLSX/Parquet), the CSV string classifier (ISO dates are validated against the calendar — `Date.parse('2024-02-30')` rolls over to March), `planHistogram`/`bucketIndex`/`histogramFromCounts` (SQLite/DuckDB build the same bins in SQL), `StatsCache` (per handle/worksheet memo of *every* outcome — successes, `skippedStats` timeouts and failures — so re-selecting a table never repeats an expensive attempt), `DistinctBudget` (one cap on tracked distinct values across all of a table's columns, on top of the per-column `MAX_TRACKED_DISTINCT`; exhausted columns report `distinctIsLowerBound` → "≥"), and `statsLimits`/`statsHooks` (mutable so tests can drive skip paths and observe errors; `statsHooks.log` exists because VS Code's extension host makes `console.warn` unassignable).
- **CSV**: types inferred from strings (integer / float / boolean / ISO date, else text; `007` stays text; blank = null); `parseCsvRows` is the single Papa config shared by `parseCsv` and `csvStats`. **XLSX**: classified from `cell.value` via `unwrapCellValue` — formulas read `cell.result`, because exceljs's `cell.value`/`effectiveType` drop falsy (`0`/`false`) formula results. **Parquet**: decoded one row group at a time (`parquetReadObjects` with `rowStart`/`rowEnd`), yielding to the event loop between groups; schema (`declaredKind`) only types columns that hold no values. Footer `statistics` are deliberately unused. **SQLite**: one aggregate scan per 40 columns; types from `typeof()` counts, not declared types. **DuckDB**: types from `DuckDBTypeId`; one aggregate scan, budgeted by `statsLimits.duckdbTimeoutMs` via `connection.interrupt()`. Histogram bounds are bound as explicit `DOUBLE`s (node-api turns a whole-number JS value into an int64 and rejects HUGEINT-sized ones). **All DuckDB connection work (`listDuckdbTables`, `readDuckdbTable`, `duckdbTableStats`) is serialized per handle by `runExclusive`**, because `interrupt()` is connection-wide and would otherwise kill another request's query; never nest `runExclusive` calls on one handle.
- **Payload must be JSON-safe** (it crosses `postMessage`): no `bigint`/`NaN`/`Infinity`/`Date`. min/max are display strings (exact text kept for integers beyond 2^53); `mean`/histogram bounds are always finite.
- **A stats failure must never break the table**: entry points catch and return `undefined`. CSV/XLSX/Parquet skip with a `skippedReason` above `statsLimits.maxCells` (20M cells; ~0.15 us/cell, measured on a 10M-cell CSV/Parquet). SQLite has its own much lower `statsLimits.sqliteMaxCells` (3M) because sql.js is synchronous and uninterruptible on the shared extension-host thread (~1 us/cell, mostly `COUNT(DISTINCT)`; a 10M-cell table blocked ~10 s). DuckDB has no cell cap (5M rows x 10 cols stats in well under a second) — it skips on timeout instead.
- **Type badges**: `KIND_INFO` in `main.js` maps each `ColumnKind` to a name and an SVG icon spec (`[tag, attrs]` shapes drawn by `renderTypeBadge` with `svgEl`; `solid: '1'` = a filled dot). Stroke/fill and the per-kind colour (`--vscode-symbolIcon-*` with `--vscode-charts-*` fallbacks) are CSS (`.type-icon`, `.type-<kind>`), never inline style. The badge is `role=img` with `aria-label`/`title` from `typeLabel` (`integer · BIGINT`). `ColumnStats.nativeType` is the source's own type name, set by `computeDuckdbStats` (`DuckDBType.toString()`), `computeSqliteStats` (`PRAGMA table_info`, by position, only when its column count matches) and `parquetNativeType`; all clipped by `clipNativeType` (60 chars). CSV/XLSX leave it unset.
- **Row virtualization** (`main.js`, `showRows`/`syncWindow`/`buildRows`): every place that fills a view's tbody (`renderTable`, `restoreOriginalRows`, `handleFilterData`) goes through `showRows(view, rows)`. Up to `VIRTUALIZE_ABOVE_ROWS` (500) rows are drawn in full; above that only rows `[start, end)` around the viewport (`ROW_OVERSCAN` 30 beyond each edge) are drawn between two `tr.row-spacer` rows whose single cell gets `style.height` through CSSOM (never a style attribute: the CSP has no `'unsafe-inline'`). One row's height is **measured** from a 20-row sample (`getBoundingClientRect` of the tbody / 20; every row is one line because cells are `nowrap`), cached in `view.rowHeight`; if it measures 0 (a hidden panel, jsdom) the table is drawn in full as before, which is why the pre-existing tests need no layout. `syncWindow` redraws only when the viewport gets within `ROW_WINDOW_MARGIN` (10) rows of an edge; the wrapper's `scroll` event is coalesced to one call per frame (`queueWindowSync`), and **anything that sets `scrollTop` from script must call `syncWindow(view)` itself** (the event is asynchronous): `restorePendingScroll`, `restoreReloadState`, `putResultScroll` do. Zebra stripes are `tr.alt` (odd row index), not `:nth-child`, because the spacers shift the parity; `.scroll-wrapper` has `overflow-anchor: none`. Row numbers are the index in the rows being shown (1..N for a filter's matches). Tests load a layout through `loadWithLayout` in `render.test.ts` (stubs `getBoundingClientRect` and `clientHeight`). Anything that later keeps per-row state (selection) must key it by row index, not DOM node.
- **Selection** (`main.js`, "Selection" section): `view.sel = { ranges: [{r0,r1,c0,c1}], kind: 'cells'|'rows'|'cols', anchor, cursor }`, by **index into `view.shownRows`** (set by `showRows` to the rows being shown: all rows, or a filter's matches), never DOM nodes, because virtualization draws only a window. `showRows` resets `view.sel` (new rows mean new indices) and `renderTable`/`syncWindow` end in `paintSelection(view)`, which toggles `is-selected`/`is-cursor` on the drawn cells only; a row's index is read from its gutter number (`rowIndexOf`), so no per-row attribute. Rows/cols ranges are whole-width/whole-height rectangles, which is what lets the row number and header light up (`paintSelection` derives it from the ranges). Gestures: `mousedown` on the wrapper (`onTableMouseDown`; ignores Alt, non-left buttons and anything inside `input/button/textarea/select/a`, so the filter boxes and profile buttons keep working; `preventDefault` stops native text selection, which is why `#csv-table td` is `user-select: none`), drag via document `mousemove`/`mouseup` (`selectionDrag`, replaces the active range), keys via `onTableKeyDown` on the wrapper (which has `tabindex=0`; with no selection the keys are left to native scrolling; Escape clears only when no stats card is open, since the card's document-level handler runs after it). `revealCell` scrolls the cursor into view: arithmetic first for a virtualized table (the row may not be drawn), then DOM geometry clear of the sticky header and gutter. **Copy** is a document-level `copy` handler that writes `selectionToTsv` (from the data, not the DOM) to `event.clipboardData`; it stands aside when an `input`/`textarea` has focus or text is natively selected. Cmd/Ctrl+Shift+C sets `copyWithHeaders` and calls `document.execCommand('copy')` so the same handler runs. `selectionSummary` (`span.selection-summary` beside, not in, `.stats-bar`) counts cells, dedupes overlapping ranges through a `Set`, and sums only when every non-empty cell matches `NUMERIC_CELL`; above `SELECTION_SCAN_CAP` (250k cells) it only counts. A reload restores the selection (`cellSelection` in `captureReloadState`, clipped to the new row count) unless a filter is being re-applied.
- **Webview UI** (`main.js`, all in the one IIFE because `render.test.ts` loads its source text directly via `vm`, so it cannot `import`): no mode control, no saved state, no Overview — every column header always gets a profile strip once its stats arrive. `renderTable` renders the table plus a `span.stats-status` (`role=status`) beside `.stats-bar` and then calls `requestStats()`; `currentView.stats` walks `idle → pending → ready | skipped | failed`, `requestStats()` posts `get-stats` once per rendered view (state flips to `pending` *before* posting, so a synchronous reply — as in tests — lands correctly), and `attachStats` appends a `button.col-profile` strip (type badge glyph, valid-vs-null bar, mini histogram / distinct-ratio bar / date range) to each existing `th` when the reply arrives — the table is never re-rendered. The status span shows "Computing…" while pending, "Statistics unavailable for this table" on failure, or the host's `skippedReason` (also as its `title`) when skipped; skipped/failed tables simply have no strips. Clicking a strip opens a non-modal **detail card** (`role=dialog`, `position: fixed`, appended to `#app`, clamped to the viewport, repositioned on scroll/resize, closed by Escape / outside press / Tab-out / re-render, focus returned to the trigger); the card also carries the "Statistics cover all N rows, not just the M shown" note. Per-column display values live in `buildColumnModels`, computed once per render.
- **Histogram bin ranges are re-derived in the webview** (`binLabel`), not shipped: it mirrors `planHistogram` in `src/columnStats.ts` (integer width `(hi-lo+1)/bins`, float `(hi-lo)/bins`). Change one, change the other — `render.test.ts` brute-forces the labels against `planHistogram`/`bucketIndex`.
- **Webview/CSP**: `style-src` has no `'unsafe-inline'`, so bars are SVG built with `createElementNS` + `setAttribute` and the card is positioned with CSSOM (`el.style.left`), never `style=""`. The status span is a sibling of `.stats-bar`, not a child — `render.test.ts` asserts the bar's exact text. Only `window`/`document`/`acquireVsCodeApi` are ESLint globals, so use `window.setTimeout`. Visual changes can't be verified in jsdom (layout, fixed positioning, z-order): check them in a scratch page that loads `media/styles.css` + `src/webview/main.js` with a stub `acquireVsCodeApi`, a strict CSP meta and `--vscode-*` theme variables, in light/dark/high-contrast. A forced-dark browser extension (Dark Reader) silently inverts a light scratch page: check `data-darkreader-mode` on `<html>` and neutralise it on the scratch page only (`documentElement.style.setProperty('filter','none','important')` through CSSOM, which the CSP allows) before judging a light render. Probe sticky layering with `document.elementFromPoint` across the header's height rather than by eye.

### Column filtering

Every column header has a filter box in a second `thead` row. Filtering is **host-side over the whole table**, like statistics: the webview sends the text as typed and the host answers with the first `tablas.maxRows` matches plus the exact match count. Syntax and semantics live in one place, the header comment of `src/filter.ts` (contains / `!` / `=` / `!=` / `=` empty / `>` `>=` `<` `<=` / `\` literal; blank boxes are dropped; AND across columns). **There is deliberately no regex operator**, so user text never reaches a regex engine on the host.

- **Protocol** (vscode-free `src/filterMessage.ts`, `isFilterMessage` guard): webview -> host `{type:'filter', seq, table?, filters:[{column,text}]}`; host -> webview `{type:'filter-data', payload:{seq, table?, rows?, matchCount?, errors?, failedReason?}}` (exactly one of rows+matchCount / errors / failedReason). `planFilter` (in `filter.ts`) decides once for all five providers: `cleared` (no reply, release caches), `invalid` (reply with `errors`, run nothing) or `run`. `seq` is **one webview-wide counter that is never reset**: the webview only applies a reply whose `seq` and `table` match its newest request, and the CSV/Parquet/SQLite/DuckDB documents keep `filterSeq` so a request that a newer one overtook while it waited on I/O (or in DuckDB's per-handle queue, or SQLite's one `setImmediate` yield) is dropped before the expensive part. Parquet re-checks it after the decode too: a clear that lands mid-decode would otherwise let the stale request re-fill `document.filterRows`. XLSX's `handleFilter` is synchronous, so it can't be overtaken and keeps no `filterSeq`. Each provider has a public `handleFilter(document, message)` next to `handleGetStats`; integration tests call it directly.
- **Three engines, one meaning.** CSV/Parquet/XLSX stringify to `FilterableRows` (`csvRowsForFilter`, `parquetRowsForFilter`, `xlsxRowsForFilter`) and share `filterTable`/`filterStringRows`; the same displayed text the table shows is what is matched. **SQLite** registers a JS UDF `tablas_match(value, i)` once per handle (sql.js arity is `func.length`, so keep exactly two parameters) that runs `stringifySqliteCell` and the *same* `compileCellPredicate`, so Unicode case folding matches (SQLite's own `lower()`/`LIKE` fold ASCII only). The query renames columns to `c0..cN` in a CTE, so views with duplicate column names work and only integers and the quoted table name are interpolated. **DuckDB** pushes down native SQL (`filterPredicateSql`, values bound with explicit types, under `runExclusive` + the `interrupt()` timeout pattern from stats). `filterPredicateSql` is a hand-written mirror of `compileCellPredicate`: **change one, change the other.** `test/unit/filterParity.test.ts` runs the shared `FILTER_CASES` (`test/unit/filterCases.ts`) against `filter.{csv,parquet,xlsx,db,duckdb}` and asserts all five return identical ids, match counts and text for columns 0-5; columns 6-7 (`d`/`ts`) hold real DATE/TIMESTAMP values (ISO strings in SQLite; real Date cells in XLSX, shown as ISO text) whose *display* differs per format (Parquet prints `2024-01-01T00:00:00.000Z`), so the test pins each format's text and only requires the filters to agree. A date operand (`>=2024-01-01`, exactly `YYYY-MM-DD`) compares at day precision: only cells starting with an ISO day take part, by their first 10 chars (`ISO_DATE_PREFIX_PATTERN`/`isIsoDateOperand` in `filter.ts`, shared with DuckDB's SQL the way `NUMBER_PATTERN` is). Month/datetime operands are still a plain string compare, and a differential test in `duckdbParser.test.ts` compares the SQL against the JS engine over VARCHAR/DECIMAL/DATE/DOUBLE/BOOLEAN/TIMESTAMP/BIGINT columns (the known differences below are deliberately not in it).
- **Known text-form differences (DuckDB only):** whole-number FLOAT/DOUBLE are printed without `.0` to match the table; non-whole 32-bit FLOAT, nested (LIST/STRUCT/MAP) and BLOB columns use DuckDB's own text form. Numeric comparisons are unaffected. SQL `trim()` strips only spaces while JS `trim()` strips all whitespace, so cells padded with tabs/newlines/NBSP differ on `=` (empty) and on number compares. DOUBLEs with magnitude >= 1e15 or < 1e-6 print in DuckDB's exponent form (`1e+15`, `1e-07`), not JS's (`1000000000000000`, `1e-7`), so an exact `=` on them misses.
- **Limits** (`filterLimits`, mutable so tests drive the skip paths): `maxCells` 20M for CSV/Parquet/XLSX (checked before decoding where the format allows); `sqliteMaxCells` 5M (rows x *filtered* columns; sql.js is synchronous and uninterruptible, measured ~0.15-0.3 us per predicate call, ~1.3 s worst case, lower than the stats budget because a filter re-runs as the user types); `duckdbTimeoutMs` 15 s; `maxTextLength` 1000 (the webview boxes carry the same `maxlength`).
- **Caching exception.** CSV/Parquet/XLSX keep the parsed string rows on the document while a filter is active (`document.filterRows`, one sheet for XLSX) when the table is within `maxCachedCells` (5M), so typing doesn't re-read and re-parse the file per keystroke; larger tables are re-parsed per request. Released when the filters are cleared and on dispose. A file edited on disk meanwhile is not noticed until then.
- **Webview** (`main.js`): a filter reply swaps **only the tbody** (`renderRows`); the header, profile strips and the focused box are never re-rendered, and the `table-fixed` choice stays based on the full table. Debounce 250 ms, Enter sends at once, Escape in a non-empty box clears it and stops propagation (so it doesn't also close an open card), the gutter `x` clears all, **Alt+click a cell** sets that column to `=value` (skipped for multi-line or over-long text, which a one-line box can't hold). Clearing restores the original rows locally with no round trip and only tells the host so it can release its cache; a table switch resets filters and does the same for the old table. Statistics are untouched by filters (the card says so while one is set) and the card is anchored below the whole `thead`, so it never covers a filter box.
- **CSS gotcha:** `thead` (not each `tr`) is `position: sticky`, and `#csv-table` uses `border-collapse: separate; border-spacing: 0`. With `collapse`, borders belong to the table and scroll away under a sticky header, leaving a gap that body text shows through (visible between the two header rows). Cells only set their own right/bottom border, so `separate` looks identical.
- **Known limitations:** boxes are trimmed, so `=` can't match a value with trailing whitespace (Alt+click skips such cells; leading spaces are fine, and a whitespace-only cell becomes `=`, i.e. "is empty"); the gutter numbers a filtered view 1..N, not the original row numbers.

### Packaging gotcha: `.vscodeignore` isn't real gitignore semantics

`@vscode/vsce`'s `.vscodeignore` matching (see `collectFiles` in its `package.js`) is **not** gitignore's last-match-wins/directory-aware negation — it's flat: a file survives if it matches *any* negate (`!...`) line, full stop, regardless of ordering or which `ignore` line "would have" excluded it. A broad `!node_modules/sql.js/**`-style re-include line silently defeats every narrower exclusion meant to trim that package down (this bit us trying to keep only `sql.js`'s `dist/sql-wasm.{js,wasm}` out of its ~30x-larger full `dist/` folder — see the comment in `.vscodeignore`). When trimming a dependency's shipped files, list exact negate patterns for only what's needed; don't try to "subtract" from a broad re-include. The DuckDB block in `.vscodeignore` follows the exact same recipe for `@duckdb/node-api`/`@duckdb/node-bindings`/`@duckdb/node-bindings-*` (its native `.node`/`.dylib`/`.so`/`.dll` files).

### Test setup

Two separate compiled outputs feed tests, both driven by `.vscode-test.mjs`:
- `unit` project: `out/test/unit/**/*.test.js`, no workspace/Electron needed conceptually but still run via `vscode-test`.
- `integration` project: `out/test/integration/**/*.test.js`, runs with `workspaceFolder: './test/fixtures'` and `extensionDevelopmentPath: '.'` — these tests open real fixture files through `vscode.commands.executeCommand('vscode.openWith', uri, 'tablas.csvViewer')` in an actual Extension Development Host.

`npm run test:unit` bypasses `vscode-test`/Electron entirely (ts-node + mocha directly against `.ts`), so use it for fast iteration on `csvParser.ts` logic. `npm test` is the only path that compiles to `out/` (via `tsc`, per `tsconfig.json`) and runs the integration suite — needed before verifying anything that touches `csvEditorProvider.ts` or the webview handshake.

Test style: `describe`/`it` (BDD), not `suite`/`test` — mocha is configured with `ui: 'bdd'` in both test projects.

Fixture paths in tests are built from `process.cwd()`, not `__dirname` — this is required for the same test file to work under both ts-node (`test:unit`) and the tsc-compiled output in `out/` (`test`).

Binary fixtures (`.parquet`, `.db`, `.xlsx`, `.duckdb`) are regenerated via `scripts/generate-parquet-fixtures.py` / `scripts/generate-sqlite-fixtures.py` / `scripts/generate-xlsx-fixtures.js` / `scripts/generate-duckdb-fixtures.js` / `scripts/generate-duckdb-legacy-fixtures.py` (needs `pip install "duckdb<2"`; writes `qualified-views.duckdb`) rather than hand-authored (each generator also writes the shared `filter.*` parity fixture; re-running a generator rewrites *every* fixture of its format with new zip timestamps/bytes, so `git checkout` the unrelated ones) — the first two need Python (`pyarrow` / stdlib `sqlite3`, respectively); the xlsx and duckdb ones are plain Node scripts using the `exceljs`/`@duckdb/node-api` runtime dependency directly, since that avoids introducing a second new dependency (e.g. `openpyxl`) just for fixture generation.

A file that `import`s `'vscode'` can never live under `test/unit/`: `npm run test:unit` runs that folder directly via ts-node with no Electron and no `vscode` module available, so it would crash the whole run. This is why there's no `sqliteEditorProvider.test.ts`/`xlsxEditorProvider.test.ts`/`duckdbEditorProvider.test.ts`/`csvEditorProvider.test.ts` under `test/unit/` despite `sqliteEditorProvider.ts`/`xlsxEditorProvider.ts`/`duckdbEditorProvider.ts` having host-side logic (`handleSelectTable`) worth covering in isolation from the webview — that coverage lives in `test/integration/sqliteEditorProvider.test.ts`/`test/integration/xlsxEditorProvider.test.ts`/`test/integration/duckdbEditorProvider.test.ts` instead, calling the provider's methods directly (bypassing `resolveCustomEditor`/the webview entirely, since there's no public API to simulate a message arriving *from* a webview).
