# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Vision

Tablas aims to become a JetBrains-style data-file editor for VS Code (think DataGrip's/IntelliJ's built-in table viewer): open a data file, see a real table, search it, edit a cell, done. See `README.md` for the user-facing pitch.

Current stage: local install only (`npm run install:local`, unpublished). Target: publish to the VS Code Marketplace under publisher `gerardovitale`. Keep marketplace-readiness in mind for anything packaging/metadata-related — `package.json` fields (`displayName`, `description`, `categories`, `keywords`, `icon`), `CHANGELOG.md` (required by `vsce`; exists, keep its `[Unreleased]` section current), and an `icon.png` are still outstanding before a first `vsce publish`. See `scripts/install-local.sh --publish-help` for the full publishing checklist.

Today: CSV, Parquet, SQLite (`.db`/`.sqlite`/`.sqlite3`), DuckDB (`.duckdb`/`.ddb`), and Excel (`.xlsx`), read-only. Planned, roughly in order:
1. **In-table find/filter** — search within the rendered table (not VS Code's plain-text Ctrl+F).
2. **Basic cell editing** — writes back to the source file; requires moving off `CustomReadonlyEditorProvider` to a real edit model (dirty state, undo/redo, save).

Keep this trajectory in mind when touching the architecture below:
- New single-table source formats should get their own parser module (parallel to `csvParser.ts`/`parquetParser.ts`) that produces the *same* `{headers, rows, rowCount, columnCount}` shape (`ParsedTable` in `src/tableData.ts`), so `src/webview/main.js` doesn't need to know or care what format it came from. New *multi-table* sources (parallel to `sqliteParser.ts`/`duckdbParser.ts`) instead produce `MultiTableParseOutcome`.
- The extension-host-parses / webview-only-renders split is the thing to preserve — don't add format-specific logic to the webview.
- Editing support will need a real `vscode.CustomDocument` implementation (currently `CsvDocument`/`ParquetDocument` are bare stubs) plus an edit/undo model — flag this explicitly if asked to implement editing rather than quietly bolting writes onto the read-only provider. `SqliteDocument`/`DuckdbDocument` are already a partial exception: each holds a live database handle (see below), but still only for read access.

## Commands

```bash
npm run compile              # esbuild both bundles (extension + webview), dev mode
npm run compile:production   # same, minified, no sourcemaps
npm run watch                # esbuild --watch, both bundles
npm run check-types          # tsc --noEmit
npm run test:unit            # fast: ts-node + mocha directly on test/unit/**, no Electron
npm test                     # full: compile + tsc (emits to out/) + vscode-test (unit + integration)
npm run install:local         # build, package, install into local VS Code (scripts/install-local.sh)
npm run install:local:quick   # same but --skip-tests
```

Run a single unit test file: `npx mocha --require ts-node/register test/unit/csvParser.test.ts`

## Architecture

Two independent esbuild bundles come out of `esbuild.js`, built together by `npm run compile`:

- `dist/extension.js` — CJS, Node platform, entry `src/extension.ts`. This is the extension host code (`main` in package.json). `papaparse`, `hyparquet`, and `exceljs` are fully bundled in here (all pure JS, no `.wasm`/native asset); `sql.js` and `@duckdb/node-api`/`@duckdb/node-bindings` are kept `external` instead (see below).
- `media/webview.js` — IIFE, browser platform, entry `src/webview/main.js`. This runs inside the VS Code webview sandbox.

**Parsing happens only in the extension host, never in the webview.** `src/csvParser.ts` wraps PapaParse and returns a `CsvParseOutcome` discriminated union (`{success: true, data, errors}` or `{success: false, errors}`). `src/csvEditorProvider.ts` reads the file, calls `parseCsv`, and posts the result to the webview as a `csv-data` message. `src/parquetParser.ts`/`src/parquetEditorProvider.ts` mirror this exactly for `.parquet`. The webview (`src/webview/main.js`) only renders pre-parsed data — it has no format-parsing logic and imports nothing from the parser modules at runtime (only referenced in JSDoc type imports).

`CsvEditorProvider` (registered as `tablas.csvViewer`, a `CustomReadonlyEditorProvider`) does a ready-handshake: it waits for a `{type: 'ready'}` message from the webview before it reads/parses the file and posts `{type: 'csv-data', payload: outcome}` back. Webview HTML is built per-request with a fresh CSP nonce (`crypto.randomBytes(16)`) and `script-src 'nonce-...'`; `default-src 'none'`.

All DOM writes in `src/webview/main.js` use `textContent`/`setAttribute` only — never `innerHTML` — this is a deliberate XSS-safety rule for any rendered cell/header content, since file content is untrusted. `eslint.config.js` has a `no-restricted-syntax` rule making this machine-checked (bans `innerHTML`/`outerHTML` assignment).

### SQLite (multi-table sources)

`.db`/`.sqlite`/`.sqlite3` files (registered as `tablas.sqliteViewer`) are the first *multi-table* source and deviate from the CSV/Parquet pattern in three ways:

- **Library**: `sql.js` (WASM SQLite), not a native binding — a single `.wasm` asset works on every platform VS Code runs on, avoiding a per-OS/arch `.vsix` matrix. It's `external` in `esbuild.js`'s extension bundle (can't be inlined — a `.wasm` binary isn't JS text) and `sqliteParser.ts` locates it via `require.resolve('sql.js/dist/sql-wasm.wasm')`.
- **Data shape**: `src/tableData.ts`'s `MultiTableParseOutcome`/`MultiTableData`/`TableRef` wrap a list of tables/views plus the currently-selected one's `ParsedTable`, additively alongside (not replacing) the single-table `TableParseOutcome` CSV/Parquet use.
- **Stateful document + bidirectional messaging**: unlike `CsvDocument`/`ParquetDocument`'s bare stubs, `SqliteDocument` (in `sqliteEditorProvider.ts`) holds the live `SqliteHandle` for the document's lifetime, so switching tables re-queries the already-open database instead of re-reading the file. `SqliteEditorProvider`'s `onDidReceiveMessage` listener stays registered after the ready-handshake (CSV/Parquet's disposes itself) to also handle `{type: 'select-table', table}` requests, responding with the same `sqlite-data` message type used for the initial load. The webview (`renderMultiTableOutcome`/`renderTableSelector` in `main.js`) renders a `<select>` above the table and posts `select-table` on change.

### XLSX (multi-table sources)

`.xlsx` files (registered as `tablas.xlsxViewer`) are the second multi-table source, reusing the exact same `MultiTableParseOutcome`/`select-table` protocol SQLite established (a workbook's sheets fill the role SQLite's tables/views do) — no webview changes were needed beyond routing a new `xlsx-data` message type to the already-generic `renderMultiTableOutcome`.

- **Library**: `exceljs`, not SheetJS's `xlsx` package — deliberately. npm's published `xlsx` is stuck at `0.18.5` with two unfixed high-severity CVEs (ReDoS + prototype pollution) triggerable by opening a crafted file; SheetJS only ships the fix via their own CDN, not npm. Since this extension's whole job is parsing untrusted file bytes, that's a direct hit on the threat model — `exceljs` has no comparable CVE in its own runtime parse path. It's pure JS (no `.wasm`), so — like `hyparquet`/`papaparse` and unlike `sql.js` — it needs no `external`/`.vscodeignore` treatment; see `xlsxParser.ts`'s `openXlsxWorkbook` for the `Buffer` typing workaround its `.d.ts` needs (an ambient `Buffer` interface it declares conflicts with `@types/node`'s generic one).
- **Cell stringification**: `stringifyXlsxCell` (in `xlsxParser.ts`) delegates to exceljs's own `cell.text` getter, which resolves formulas to their cached result — unlike `parquetParser.ts`'s `stringifyCell`, no manual type-switching is needed. Note `cell.text` does **not** apply the cell's number format (a `0%` cell shows `0.5`, and a Date cell renders as a JS `Date.toString()`), and renders a formula result of `0`/`false` as `''`.
- **Stateful document + bidirectional messaging**: same shape as SQLite — `XlsxDocument` (in `xlsxEditorProvider.ts`) holds the parsed `Workbook` for the document's lifetime (nothing to `.close()`, unlike `SqliteHandle`), and `XlsxEditorProvider`'s message listener stays registered post-handshake to handle `{type: 'select-table', table}` (the field is still named `table`, reused as-is from the SQLite protocol) by re-reading the already-parsed workbook for a different sheet.

### DuckDB (multi-table sources)

`.duckdb`/`.ddb` files (registered as `tablas.duckdbViewer`) are the third multi-table source, reusing the same `MultiTableParseOutcome`/`select-table` protocol via a new `duckdb-data` message type routed to the already-generic `renderMultiTableOutcome` — no webview changes beyond that one dispatch line.

- **Library**: `@duckdb/node-api` (the official Node "Neo" client), a **native** N-API binding — a deliberate departure from `sql.js`'s WASM-for-portability precedent (see the SQLite section above), chosen for full DuckDB SQL support and native speed. Its per-platform binary (`@duckdb/node-bindings-<platform-arch>`, ~100+ MB uncompressed, resolved transitively via `@duckdb/node-bindings`) means a single `.vsix` is no longer portable across platforms the way `sql.js`'s one `.wasm` file was — see the Packaging note below. Both `@duckdb/node-api` and `@duckdb/node-bindings` are `external` in `esbuild.js` (a native `.node` binary can't be bundled by esbuild), and both need narrow `.vscodeignore` allowlist entries (see the flat-negate gotcha below).
- **Bytes vs. path**: unlike `sql.js`/`exceljs`, `@duckdb/node-api` opens a database from a file *path*, not an in-memory byte buffer. To keep `parseDuckdb(bytes, ...)` symmetric with `parseSqlite`/`parseXlsx` (same signature, same fixture-bytes unit-test style, and correctness over non-local `vscode.FileSystemProvider` filesystems), `duckdbParser.ts`'s `openDuckdbDatabase` writes `bytes` to a temp file (`os.tmpdir()`) and opens DuckDB against that; `DuckdbHandle.close()` deletes the temp file alongside closing the connection/instance.
- **Read-only opens**: `openDuckdbDatabase` always opens with `{ access_mode: 'READ_ONLY' }` so the viewer never mutates the source file. This means any test that needs to *write* to a DuckDB file (e.g. building an ad-hoc fixture inline) has to go around `openDuckdbDatabase` and use `DuckDBInstance.create` directly, the same way `scripts/generate-duckdb-fixtures.js` does.
- **Cell stringification**: `stringifyDuckdbCell` (in `duckdbParser.ts`) consumes `DuckDBResultReader.getRowsJson()`, which already reduces DuckDB's richer type system (BIGINT/HUGEINT/DECIMAL/DATE/TIMESTAMP/UUID/BLOB, etc.) to JSON-safe strings/numbers/booleans — notably, BIGINT comes through as an exact string, avoiding the precision loss `stringifySqliteCell` accepts as a known limitation for sql.js's plain-`number` BIGINTs. Only nested LIST/STRUCT/MAP/ARRAY/UNION values need any handling here (via `JSON.stringify`), similar in spirit to `parquetParser.ts`'s `stringifyCell`.
- **Table/view listing**: `listDuckdbTables` queries `information_schema.tables` (`table_type = 'VIEW'` vs. everything else), rather than SQLite's `sqlite_master`.
- **Stateful document + bidirectional messaging**: same shape as SQLite/XLSX — `DuckdbDocument` (in `duckdbEditorProvider.ts`) holds the live `DuckdbHandle` (and its temp file) for the document's lifetime, and `DuckdbEditorProvider`'s message listener stays registered post-handshake to handle `{type: 'select-table', table}`. One difference: `handleSelectTable` is `async` here (DuckDB reads are all promise-based), unlike `SqliteEditorProvider`'s synchronous version.

**Packaging note**: `scripts/install-local.sh` runs a plain `vsce package` (no `--target`), which is fine for local single-machine install since npm only installs the dev machine's matching `@duckdb/node-bindings-<platform-arch>` package. A future Marketplace publish will need **per-platform `.vsix` builds** (`vsce package --target darwin-arm64`, etc.) — add this to the "outstanding before `vsce publish`" list above when that work starts; it hasn't been built yet.

### Column statistics

Column statistics (`TableStats`/`ColumnStats` in `src/tableData.ts`; `columns[i]` parallels the table's headers) are **lazy**: rows are posted first and never carry stats. The first time the user turns the **Statistics** view on (Headers or Overview) — or on load, if a saved "on" mode is restored, or when a new table is shown while a mode is on — the webview posts `{type:'get-stats', table?}` and the provider answers `{type:'stats-data', payload:{table?, stats?}}` (types + guards in the vscode-free `src/statsMessage.ts`). `stats` undefined = failed; `skippedReason` inside it = deliberately skipped. The echoed `table` lets the webview drop a stale reply. Stats cover the **whole table** (never limited by `tablas.maxRows`) and cost nothing for users who never open the view.

Each provider exposes a public `handleGetStats(document, table?)` next to `handleSelectTable` (integration tests call it directly — a webview→host message can't be simulated) and answers it from the same persistent message listener. **CSV and Parquet keep no parsed state, so they re-read (and re-parse) the file on demand** rather than hold rows/bytes for the editor's lifetime; a file edited on disk in between yields stats for its newer content. XLSX/SQLite/DuckDB use the workbook/handle the document already retains.

Why stats live in the parsers: every parser stringifies cells and maps NULL to `''`, so types and nulls are gone once `rows` exists. Each parser exports a standalone entry point that computes from native values (CSV/XLSX/Parquet) or SQL push-down (SQLite/DuckDB): `csvStats(raw)`, `xlsxSheetStats(ws)`, `parquetStats(bytes)`, `sqliteTableStats(handle, table)`, `duckdbTableStats(handle, table)`. All return `TableStats | undefined`, never throw, and report unexpected errors through `statsHooks` (`console.warn` by default).

- `src/columnStats.ts` (no `vscode` import) holds the shared pieces: `ColumnStatsAccumulator` (CSV/XLSX/Parquet), the CSV string classifier (ISO dates are validated against the calendar — `Date.parse('2024-02-30')` rolls over to March), `planHistogram`/`bucketIndex`/`histogramFromCounts` (SQLite/DuckDB build the same bins in SQL), `StatsCache` (per handle/worksheet memo of *every* outcome — successes, `skippedStats` timeouts and failures — so re-selecting a table never repeats an expensive attempt), `DistinctBudget` (one cap on tracked distinct values across all of a table's columns, on top of the per-column `MAX_TRACKED_DISTINCT`; exhausted columns report `distinctIsLowerBound` → "≥"), and `statsLimits`/`statsHooks` (mutable so tests can drive skip paths and observe errors; `statsHooks.log` exists because VS Code's extension host makes `console.warn` unassignable).
- **CSV**: types inferred from strings (integer / float / boolean / ISO date, else text; `007` stays text; blank = null); `parseCsvRows` is the single Papa config shared by `parseCsv` and `csvStats`. **XLSX**: classified from `cell.value` via `unwrapCellValue` — formulas read `cell.result`, because exceljs's `cell.value`/`effectiveType` drop falsy (`0`/`false`) formula results. **Parquet**: decoded one row group at a time (`parquetReadObjects` with `rowStart`/`rowEnd`), yielding to the event loop between groups; schema (`declaredKind`) only types columns that hold no values. Footer `statistics` are deliberately unused. **SQLite**: one aggregate scan per 40 columns; types from `typeof()` counts, not declared types. **DuckDB**: types from `DuckDBTypeId`; one aggregate scan, budgeted by `statsLimits.duckdbTimeoutMs` via `connection.interrupt()`. Histogram bounds are bound as explicit `DOUBLE`s (node-api turns a whole-number JS value into an int64 and rejects HUGEINT-sized ones). **All DuckDB connection work (`listDuckdbTables`, `readDuckdbTable`, `duckdbTableStats`) is serialized per handle by `runExclusive`**, because `interrupt()` is connection-wide and would otherwise kill another request's query; never nest `runExclusive` calls on one handle.
- **Payload must be JSON-safe** (it crosses `postMessage`): no `bigint`/`NaN`/`Infinity`/`Date`. min/max are display strings (exact text kept for integers beyond 2^53); `mean`/histogram bounds are always finite.
- **A stats failure must never break the table**: entry points catch and return `undefined`. CSV/XLSX/Parquet skip with a `skippedReason` above `statsLimits.maxCells` (20M cells; ~0.15 us/cell, measured on a 10M-cell CSV/Parquet). SQLite has its own much lower `statsLimits.sqliteMaxCells` (3M) because sql.js is synchronous and uninterruptible on the shared extension-host thread (~1 us/cell, mostly `COUNT(DISTINCT)`; a 10M-cell table blocked ~10 s). DuckDB has no cell cap (5M rows x 10 cols stats in well under a second) — it skips on timeout instead.
- **Webview UI** (`main.js`, all in the one IIFE because `render.test.ts` loads its source text directly via `vm`, so it cannot `import`): a 3-way segmented control **Off / Headers / Overview**, saved with `vscode.setState` (default Off; restored via `getState`, invalid values ignored). Modes switch by toggling a `show-profile` class on `#csv-table` and the `hidden` attribute on `#stats-panel` — the table is never re-rendered. `renderTable` always renders the control and an empty panel; `currentView.stats` walks `idle → pending → ready | skipped | failed`, `requestStats()` posts `get-stats` once per rendered view (state flips to `pending` *before* posting, so a synchronous reply — as in tests — lands correctly), and `attachStats` fills the panel and appends the strips to the existing `th`s when the reply arrives. A status span (`role=status`) shows "Computing…" / "Statistics unavailable for this table"; a failed table disables Headers/Overview without touching the saved mode. *Headers* puts a `button.col-profile` strip (type badge glyph, valid-vs-null bar, mini histogram / distinct-ratio bar / date range) in every column `th`; clicking it opens a non-modal **detail card** (`role=dialog`, `position: fixed`, appended to `#app`, clamped to the viewport, repositioned on scroll/resize, closed by Escape / outside press / Tab-out / mode change / re-render, focus returned to the trigger). *Overview* is the one-row-per-column list; clicking a row scrolls that column into view and flashes its header. Per-column display values live in `buildColumnModels`, computed once per render.
- **Histogram bin ranges are re-derived in the webview** (`binLabel`), not shipped: it mirrors `planHistogram` in `src/columnStats.ts` (integer width `(hi-lo+1)/bins`, float `(hi-lo)/bins`). Change one, change the other — `render.test.ts` brute-forces the labels against `planHistogram`/`bucketIndex`.
- **Webview/CSP**: `style-src` has no `'unsafe-inline'`, so bars are SVG built with `createElementNS` + `setAttribute` and the card is positioned with CSSOM (`el.style.left`), never `style=""`. The mode control is a sibling of `.stats-bar`, not a child — `render.test.ts` asserts the bar's exact text. Only `window`/`document`/`acquireVsCodeApi` are ESLint globals, so use `window.setTimeout`. Visual changes can't be verified in jsdom (layout, fixed positioning, z-order): check them in a scratch page that loads `media/styles.css` + `src/webview/main.js` with a stub `acquireVsCodeApi`, a strict CSP meta and `--vscode-*` theme variables, in light/dark/high-contrast.

### Packaging gotcha: `.vscodeignore` isn't real gitignore semantics

`@vscode/vsce`'s `.vscodeignore` matching (see `collectFiles` in its `package.js`) is **not** gitignore's last-match-wins/directory-aware negation — it's flat: a file survives if it matches *any* negate (`!...`) line, full stop, regardless of ordering or which `ignore` line "would have" excluded it. A broad `!node_modules/sql.js/**`-style re-include line silently defeats every narrower exclusion meant to trim that package down (this bit us trying to keep only `sql.js`'s `dist/sql-wasm.{js,wasm}` out of its ~30x-larger full `dist/` folder — see the comment in `.vscodeignore`). When trimming a dependency's shipped files, list exact negate patterns for only what's needed; don't try to "subtract" from a broad re-include. The DuckDB block in `.vscodeignore` follows the exact same recipe for `@duckdb/node-api`/`@duckdb/node-bindings`/`@duckdb/node-bindings-*` (its native `.node`/`.dylib`/`.so`/`.dll` files).

### Test setup

Two separate compiled outputs feed tests, both driven by `.vscode-test.mjs`:
- `unit` project: `out/test/unit/**/*.test.js`, no workspace/Electron needed conceptually but still run via `vscode-test`.
- `integration` project: `out/test/integration/**/*.test.js`, runs with `workspaceFolder: './test/fixtures'` and `extensionDevelopmentPath: '.'` — these tests open real fixture files through `vscode.commands.executeCommand('vscode.openWith', uri, 'tablas.csvViewer')` in an actual Extension Development Host.

`npm run test:unit` bypasses `vscode-test`/Electron entirely (ts-node + mocha directly against `.ts`), so use it for fast iteration on `csvParser.ts` logic. `npm test` is the only path that compiles to `out/` (via `tsc`, per `tsconfig.json`) and runs the integration suite — needed before verifying anything that touches `csvEditorProvider.ts` or the webview handshake.

Test style: `describe`/`it` (BDD), not `suite`/`test` — mocha is configured with `ui: 'bdd'` in both test projects.

Fixture paths in tests are built from `process.cwd()`, not `__dirname` — this is required for the same test file to work under both ts-node (`test:unit`) and the tsc-compiled output in `out/` (`test`).

Binary fixtures (`.parquet`, `.db`, `.xlsx`, `.duckdb`) are regenerated via `scripts/generate-parquet-fixtures.py` / `scripts/generate-sqlite-fixtures.py` / `scripts/generate-xlsx-fixtures.js` / `scripts/generate-duckdb-fixtures.js` rather than hand-authored — the first two need Python (`pyarrow` / stdlib `sqlite3`, respectively); the xlsx and duckdb ones are plain Node scripts using the `exceljs`/`@duckdb/node-api` runtime dependency directly, since that avoids introducing a second new dependency (e.g. `openpyxl`) just for fixture generation.

A file that `import`s `'vscode'` can never live under `test/unit/`: `npm run test:unit` runs that folder directly via ts-node with no Electron and no `vscode` module available, so it would crash the whole run. This is why there's no `sqliteEditorProvider.test.ts`/`xlsxEditorProvider.test.ts`/`duckdbEditorProvider.test.ts`/`csvEditorProvider.test.ts` under `test/unit/` despite `sqliteEditorProvider.ts`/`xlsxEditorProvider.ts`/`duckdbEditorProvider.ts` having host-side logic (`handleSelectTable`) worth covering in isolation from the webview — that coverage lives in `test/integration/sqliteEditorProvider.test.ts`/`test/integration/xlsxEditorProvider.test.ts`/`test/integration/duckdbEditorProvider.test.ts` instead, calling the provider's methods directly (bypassing `resolveCustomEditor`/the webview entirely, since there's no public API to simulate a message arriving *from* a webview).
